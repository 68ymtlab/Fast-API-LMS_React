# AI チューター — 今後の方向性と、演習問題を「生成・作成」する方法の考察

作成: 2026-08-23 / 前提資料: [`ai-tutor.md`](ai-tutor.md)（配置）・[`ai-tutor-data.md`](ai-tutor-data.md)（データ設計）・[`ai-tutor-handover.md`](ai-tutor-handover.md)（運用）

---

## 0. 結論（先に）

1. **学生に見せる問題を LLM がその場で生成することは、引き続きやらない。** 研究側（`agents/workspace/rag/reports/tutoring_system_architecture.md`）の決定「演習のその場生成は無し（LLM 生成の問題は誤りうるため危険）」は正しく、LMS 側もそれに従う。
2. ただし **「作成を助ける」ことは別**。安全に問題を増やす道は 3 本あり、上から順に導入する:
   - **(A) テンプレート × パラメータ × 計算機検証**（正解が機械的に確定する問題種だけ。LLM 不要。誤り率ほぼ 0）
   - **(B) LLM 起草 → 機械検証 → 教員承認**（KG の節・学生のつまずきを種に下書きを作り、検証器を通過し教員が承認したものだけ `questions` に入る）
   - **(C) 既存問題のバリアント**（数値だけ差し替え、検証付き。(A) の特殊形）
3. どの道でも **「未承認の問題は学生に出さない」「出所（provenance）と検証結果を問題に持たせる」「撤回できる」** を仕組みで保証する。
4. 学生が解いた結果（正誤・👎・混乱）から **「どの概念に問題が足りないか」** を出す需要推定を先に作る。作る量より、どこに作るかが効く。
5. **作問支援より先に直す土台がある**（§10 批評の反映）: 撤回が効かない経路、クライアント側採点と正解の送出、宿題貼り付けへの無防備、対照群の無い効果測定、`public.questions` への書き込み経路を権限・テスト無しで足さないこと。

## 1. 現状の立ち位置（何があって、何が無いか）

| ある | 無い |
|---|---|
| 教員が作った既存問題を話題に合わせて出す（類似度・解答履歴・タグ・習熟度・繰り返し抑止） | 問題の**供給**（線形代数はデモ 12 問のみ。教員の作問負担が大きい） |
| 1 問をチューター内で解答・採点・記録 | 概念ごとの「問題の空白」を可視化する仕組み |
| KG（672 エンティティ、節構造、前提／発展） | KG から問題を組み立てる仕組み |
| LLM 呼び出しの JSON 拘束（`response_format`）、埋め込みランキング、節対応 | 問題の**検証器**（SymPy 等）と、教員の**レビューキュー** |
| 教員ビュー（質問・ページ別・学生別・つまずく問題・週次品質・👎） | 「ここに問題を作るべき」という提案 |

LMS の問題形式（`questions.question_type` / `content_data`）は `numeric`（`answers[]`, `tolerance`）、`multiple_numeric`（`blanks[{blank_id,label,answers,tolerance}]`）が実在し、採点は既存演習ページの `checkAnswer`（許容誤差つき数値比較）。`mcq` / `descriptive` も採点コードに分岐はある。数式は Markdown 経由なので `\\` を二重化して保存する流儀。

## 2. なぜ「その場生成」は危険で、「作成支援」なら許されるのか

- 誤りの**被害の出方**が違う。その場生成は誤った問題が**検証も人の目も通らず**学生に届く。作成支援は「検証器 → 教員」の 2 段の関所を通った問題だけが学生に届く。
- **責任の所在**が明確になる。承認した教員の問題として出るので、学生にとっても「先生の問題」。
- 研究側の UX 教訓（確認クイズ probe は「ウザい」）も、**問題はチューターが押し付けるのではなく、学生が解きたいときに 1 問だけ**（現状の UI）で守れる。
- 注意（批評より）: probe 却下の根拠は開発者本人 n=1 の評価で、学習科学のテスト効果（望ましい困難）とは整合しない。研究側文書とプロンプトの「出題禁止」は **「回答毎・強制の出題の禁止」** に限定して読み、**学生が選ぶ・スキップ可・最大 1 回**の産出機会（現状の関連問題カード）は許容し、効果は A/B で測る（§6）。研究側 `tutoring_system_architecture.md` §0/§6 にも「学生向けその場生成は無し／教員承認つき作問支援は別系統」の but 書き（carve-out）を入れてもらうのが整合的。
- 研究側自身が LLM 生成物を採用した唯一の実績は評価セット（hybrid_v2）で、**人手監査・清掃・生成バイアス監査（E7）** を経てから。Phase 6 のスコープ外にも「SymPy 等による数式の厳密検証」「前提グラフに基づく問題の自動**選定**」が明記されている。→ 許容条件は「人手（教員/TA）監査つき」「数式は形式検証」「生成元バイアスを監査」。

## 3. 方式の比較

| | (A) テンプレート＋計算機 | (B) LLM 起草＋検証＋承認 | (C) 既存問題のバリアント | (D) 需要推定（どこに作るか） |
|---|---|---|---|---|
| 正しさの保証 | **計算機が正解を出す**（SymPy/NumPy）。テンプレ文言の誤りは作成時に 1 回レビュー | 検証器（数値・記号）を通過＋教員承認。検証できない形式は承認必須 | 元問題の構造を保ち数値のみ → 計算機で正解 | 該当なし（提案のみ） |
| LLM 呼び出し | 0 | 1〜2 回／問（起草・解説） | 0（文面の自然さ補正に 1 回任意） | 0〜1 |
| 人手 | テンプレ設計（1 種 30 分〜1 時間）、以後自動 | 承認 1 問 1〜2 分 | ほぼ不要 | 不要 |
| 作れる幅 | 計算問題（行列式・逆行列・階数・固有値・内積・一次独立・連立・1 次変換）。概念理解の問いは苦手 | 概念・証明の骨子・反例・応用など広い | 元問題と同型のみ | — |
| 研究方針との整合 | ◎ | ○（「生成」だが教員承認で学生に出る） | ◎ | ◎ |
| 導入順 | **1** | 3 | 2 | **0（先に）** |

### 3.1 (A) テンプレート × パラメータ × 計算機検証 — 具体像

```
テンプレート（教員または開発者が 1 回書く）
  id: det2x2
  統一概念: 行列式（KG 節「一般の行列式」にリンク）
  文面: 行列 $\\begin{pmatrix}{a}&{b}\\\\{c}&{d}\\end{pmatrix}$ の行列式を求めよ。
  パラメータ: a,b,c,d ∈ [-5,5] の整数（難易度 1: 0 を含めない・|値|≤3 / 難易度 2: ≤5 / 難易度 3: 分数あり）
  正解: sympy.Matrix([[a,b],[c,d]]).det()   ← 計算機が出す
  形式: numeric（tolerance 0）
  制約: 正解が 0 にならない（識別力）、同じ組を出さない（既出チェック）
  解説: 「ad−bc = …」をテンプレで展開（LLM 不要）
```

候補（線形代数、すべて SymPy で正解確定）: 2×2/3×3 行列式、逆行列の成分、階数、固有値（整数固有値になる行列を逆算生成）、固有ベクトル（比を問う）、内積・ノルム・なす角、一次独立の判定（整数ベクトル、最大独立本数）、連立 1 次方程式（解が整数になるよう先に解から係数を作る）、1 次変換の像の座標、転置・積の成分。

注意点: **「解から問題を作る」**（固有値・連立は先に答えを決めて行列を逆算）と整数で綺麗になる。識別力のために「答えが 0 / 1 / 対称すぎる」などの退屈なケースは除外。
- **実行時にその場でインスタンス化しない**。テンプレから事前に N 問を材料化（`problem_drafts` → 承認 → `questions`）し、テンプレ単位で property-based test（SymPy の正解と採点器の一致、表記の描画）を通す。承認も「テンプレ単位」で済ませ、個々の数値は自動（教員負担を 1 問 1 分から「1 種 1 回」に下げる）。
- **分数は当面出さない**: 既存の採点器は `parseFloat`＋絶対 `tolerance`（`set/[set_id]/page.tsx` の `checkAnswer`）で、分数・全角入力が不正解になる。難易度 3「分数あり」は入力パーサを拡張してから。偽不正解は需要推定にも逆流する。
- **概念理解の問いも (A) に含める**: 需要推定の種は「概念的つまずき」が多いので、計算問題だけでは供給がずれる。SymPy で真偽を確定できる mcq（例: 「次のうち正則な行列はどれか」「この 2 ベクトルは一次独立か」）をテンプレ化し、誤答肢はよくある誤り（行列式の符号ミス等）を機械的に作る。

### 3.2 (B) LLM 起草 → 機械検証 → 教員承認 — 具体像

```
種（seed）: KG の節／エンティティ（定義・定理）、学生のつまずき（👎 コメント・混乱の多い概念・不正解の多い問題）、教員の指示（「固有値の意味を問う 3 択を 5 問」）
   ↓ LLM（JSON Schema で拘束: {question_type, statement, answers|choices, solution_steps, concept, difficulty, prerequisites}）
   ↓ 機械検証
      - numeric/multiple_numeric: 解答の値を SymPy で再計算し一致を要求（問題文から式を抽出できる形式に限定: テンプレ穴埋め or 構造化フィールド）
      - mcq: 正解が 1 つだけ、選択肢が相互排他、誤答が「よくある誤り」であることを別呼び出しで自己検査（弱い保証）
      - 表記: MathJax で描画できるか（\\ 二重化、未閉じの $）、文字数、禁止語
      - 重複: 既存問題との埋め込み類似度（related.py と同じ bge-m3）が閾値以上なら「既存と重複」フラグ
      - 教科書転載: 教科書本文との n-gram 一致率が高い文は書き換えを要求（著作権）
   ↓ レビューキュー（教員画面）: 検証結果バッジ付きで一覧、編集・承認・却下・差し戻し
   ↓ 承認 → questions に INSERT（provenance: generated_by=llm, model, seed, verifier, approved_by, approved_at）
   ↓ 学生には「承認済み」だけが出る。問題に誤りが見つかったら「撤回」（is_active=false）で即時に全経路から消える
```

- **検証できないもの（記述式・証明）は、機械検証を「表記と重複」だけにし、教員承認を必須**にする。
- 検証器の穴（批評より）を先に塞ぐ: (1) numeric は「文面 ⇔ 構造化フィールド」の不一致を機械では検出できない → **文面はテンプレから機械生成**（LLM には構造化フィールドと言い換え候補だけ起草させる）。(2) `solution_steps`（解説）は検証できない → 教員が読むか、学生には出さない。(3) mcq の「同族 LLM による自己検査」は合格判定に**数えない**（研究側の judge は人手検証 κ≥0.6 が未了）。教員承認必須。
- (B) は **教員が明示的に要求する pull 型のみ**（勝手にキューを溜めない）。キューが N 件を超えたら生成を止める。教員の閲覧・承認ログで関与量を計測し、起草 50 問のパイロットで誤り率とレビュー時間を実測してから Go/No-Go。
- LLM への入力は **KG のエンティティ本文（定義・定理・例）**と教科書の節を文脈に入れ、「教科書の記法・記号に合わせる」「教科書外の概念を持ち込まない」を指示。これは回答生成と同じ `generate_answer` の枠組み（`page_context` / 節ヒント）で実現できる。
- 1 問あたり LLM 1〜2 回（起草＋解説）。失敗率は初期 20〜30% と見込み、検証で落とす前提で量を出す。

### 3.3 (C) 既存問題のバリアント

既存 `numeric` 問題の文面から数値を抽出して置換し、正解を再計算できる場合のみ。抽出が曖昧なら諦める（安全側）。効果: 「同じ問題を繰り返さない」ルールと相性がよく、再提示の代わりにバリアントを出せる。

### 3.4 (D) 需要推定 — 先に作る

すでに `tutor` スキーマにある材料で出せる:
- **概念別の質問数・混乱**（`turns.focus_concept`）に対して、その概念にタグ付いた問題数（`question_tags`）が少ない → 「問題の空白」
- **不正解が多い問題**（`question_exposures.status_at_show='wrong'`、`student_answers`）→ 同型のバリアントや一段易しい前提問題の需要
- **👎 コメント**（`turn_feedback`）→ 説明不足の概念
- KG の **前提→発展の経路上で問題が無い節** → 学習経路の穴

出力は教員ビューに「問題が足りない概念 TOP10（質問数／既存問題数／提案する問題種）」として表示し、そこから (A)(B) の生成を起動できるようにする。
- 前提の修正（批評より）: `turns.focus_concept` は KNOWN_CONCEPTS 一致／ページタイトル／生クエリ先頭 24 文字で決まりノイズが大きく、`tags.name`・KG 節との対応表が無い。**教員ビューで編集できる対応辞書（概念 ↔ タグ ↔ KG 節）を先に作る**。
- `question_tags` / `student_answers` は `public` なので、需要推定の集計は **backend 側**で実装する（`tutor_app` は `public` を読めない方針）。tutor は `turns` / `exposures` / `feedback` の集計だけ返す。
- 実データが 2〜4 週分溜まるまで結論を出さない（デモ 12 問・テストユーザーの履歴で判断しない）。

## 4. データ設計（追加するもの）

```
tutor.problem_templates     id, key, concept, kg_section, question_type, statement_tmpl, params_spec(jsonb), solver(識別子), difficulty_rules(jsonb), explanation_tmpl, created_by, is_active
tutor.problem_drafts        id, source(template|llm|variant), seed(jsonb), question_type, content_data(jsonb: LMS 形式そのまま), concept, kg_section,
                            verify_result(jsonb: {numeric_ok, duplicate_score, notation_ok, plagiarism_score, notes}), status(draft|verified|approved|rejected|withdrawn),
                            model, prompt_version, created_at, reviewed_by, reviewed_at, review_note, published_question_id
```
- 承認時に `public.questions` へ INSERT するのは **backend**（`public` に書くのは backend の責務。tutor は `tutor` スキーマのみ、の方針を維持）。tutor は下書き・検証・キューまで。
- provenance の置き場（批評より）: `questions` に owner/source/approved_by の列は無く、`content_data` 内に置く案は **`PUT /questions/{id}` の全置換で消える**うえ `/courses/{id}/questions` で学生にも見える。→ **`tutor.published_questions`（question_id, draft_id, template_id, source, verifier_result, approved_by, approved_at, withdrawn_at）** を tutor 側に持つ（列追加は別途検討）。`template_id` で一括撤回できるようにする。
- **撤回が効くように既存の穴を塞ぐ**: 学生の演習ページは `/courses/{id}/questions` を `include_inactive=True` 既定で取得し、フロントで `is_active` を見ていない（`lessons_router.py` / `set/[set_id]/page.tsx`）。`is_active=false` だけでは消えない。学生向け API で `is_active` を強制し、`exercise_sets.question_ids` からも外す処理を撤回フローに含める（関連問題カード側は既に `is_active==True` で絞っている）。
- **承認した問題は演習セットに割り当てる**: `student_answers` は `exercise_sessions(exercise_set_id)` 経由でしか記録できず、セット外の問題はチューターのカードで「記録されません」になる。承認フローに「コース別の演習セットへ追加」を含める（そうしないと再提示・需要推定に乗らない）。
- 学生側に **「問題を報告」**（`tutor.question_reports`: question_id, student_id, reason, created_at）を付けないと、合格ライン「承認後に誤りが見つかった率」が観測できない。

## 5. 統合点（LMS のどこに載るか）

| 画面／API | 役割 |
|---|---|
| 教員ビュー `/t/tutor` に「問題作成支援」タブ | 需要推定の一覧 → 「この概念に (A) で 5 問作る」「(B) で起草する」→ レビューキュー（検証バッジ・編集・承認・却下） |
| backend `/api/tutor/admin/drafts`（GET/POST/approve/reject） | tutor の下書き API を中継し、承認時に `questions` へ INSERT（`require_teacher_or_higher`） |
| tutor `/admin/generate/template`, `/admin/generate/llm`, `/admin/verify`, `/admin/drafts` | 生成・検証・キュー |
| 学生側 | 承認済み問題は既存の関連問題カードと演習ページに流れるが、**変更が要る点**: (1) カードのその場採点は numeric / multiple_numeric のみ（mcq / descriptive は `grade()` が null、descriptive は演習ページでも完全一致採点）→ (B) の mcq／記述式は採点経路を先に設計するか対象外。(2) **正解が backend から学生ブラウザに送られ、採点も `is_correct` もクライアント決定**（`grading.answers`、`RelatedQuestions.tsx grade()`、`POST /exercise-sessions/{id}/answers`）→ チューター経路だけでもサーバー側採点・「答えを確認」はサーバーで試行後にだけ返す形に直す。(3) 不正解時に解説／ヒント→「この問題についてチューターに聞く」導線を付ける（供給を増やす前に）。(4) `RelatedRankRequest.candidates` の上限 2000 を超えると 422 でカードが黙って消える→全件ロードと上限を直す |

依存の追加: tutor に `sympy`（検証器）。LLM は既存の `_chat_json`（JSON Schema 拘束）。

## 6. 評価と段階導入

| 段階 | 内容 | 合格ライン |
|---|---|---|
| 0 | 需要推定タブ（読み取りのみ） | 教員が「納得できる」一覧か（定性） |
| 1 | (A) テンプレ 5 種（行列式・逆行列・内積・階数・固有値）を承認フロー付きで | 機械検証の誤り率 0、教員の修正率 < 5% |
| 2 | (C) バリアント（既存 numeric 問題） | 同上 |
| 3 | (B) LLM 起草（numeric と mcq のみ、検証必須）をパイロット 1 クラス | 検証通過率 ≥ 70%、教員の承認率 ≥ 60%、承認後に誤りが見つかった率 < 1% |
| 4 | (B) を記述式へ拡張（教員承認必須） | 教員の負担（1 問あたり分）と満足度 |

学生側の効果指標（批評で修正）: **対照群なしでは自己選択と区別できない**ので、学生ハッシュで A/B 割当（関連問題カードの表示／次の一歩／gap clarify の有無）を行い `turns.variant` に記録する。主要アウトカムは「説明後の関連問題の初回正答」「同概念の後続 confused 率」「演習セット／小テストの成績」。👍👎 は品質の参考値とし KPI から外す。受動レベル推定（0.917 > 0.896）は LLM 模擬学習者 n=48 の結果で実学習者では未検証 → 教員ビューの理解度表示に注記する。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 検証を通った問題が文面として曖昧（答えは合うが問いが不明瞭） | 教員承認を外さない（(A) でもテンプレ文面は教員が 1 回確認）。学生の 👎・正答率異常で撤回 |
| 教員がレビューしない（キューが溜まる） | 1 問 1 分で済む UI（差分表示・ワンクリック承認）、週次サマリで通知、(A) は「テンプレ単位」で承認（個々の数値は自動） |
| 数式表記・許容誤差の事故 | 生成側で LMS の流儀（`\\` 二重化、`tolerance` 明示）を強制し、描画プレビューを必須に |
| 教科書本文の転載 | n-gram 一致検査、「言い換え」を LLM に要求 |
| 学生が答えを見るだけ | 現状どおり「答えを確認」は一度解答を試した後。正解の丸暗記対策は (A)(C) の数値バリアントで |
| 問題の供給が偏る | 需要推定で空白を埋める方向に誘導 |
| **課題・宿題の貼り付け**（回答プロンプトのルール 2「最初に一言で答え」がそのまま解答機になる） | homework-like 検出（問題文の丸写し・「解いて」・番号付き設問）→「次の一手だけ」モードに切替え、`turns` に記録。研究側 core のプロンプト変更 1 人日。**P0** |
| LLM／埋め込み／リランカー停止時の振る舞い（単一エンドポイント依存） | 依存先 health を `/health` に含め、停止時は「今は答えられません」の縮退応答。関連問題・振り返りは落ちても会話は続ける |
| 権限（担当コース外の教員が質問一覧を見る、他人の会話へのフィードバック） | `/api/tutor/questions|admin/*` にコース担当チェック、feedback の所有チェック（turn_id が本人の会話か） |
